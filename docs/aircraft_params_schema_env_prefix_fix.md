# Aircraft parameters page renders only "Configuration" on DEV/QA

Analysis + fix record. Written 2026-07-15.

**TL;DR** The configurator's Aircraft parameters page shows every section on
prod but only the first ("Configuration") section on DEV/QA, because
`aircraft_params_schema.json` was never published to the env-scoped R2 prefixes
(`assets/editor/dev/`, `assets/editor/qa/`) — only to the bare prod prefix. The
page fetches a 404, parses the error body as its schema, and dies rendering an
`undefined` group list. Immediate fix (hand-upload to dev/qa) is **done**; two
durable follow-ups are planned.

## Symptom

- Prod `https://pyefis.aerocommons.org/aircraft?project=1` — full page, sections
  from "Configuration" through "AOA (calibration placeholder)".
- DEV `https://pyefis-dev.aerocommons.org/aircraft?project=1` — only the first
  "Configuration" section; everything below it is missing.

## Root cause

The "Configuration" card is **static HTML** and always renders
(`configurator/public/aircraft.html:68-91`). Every section below it is built by
`render()` from `schema.groups`. The schema is fetched in `boot()`:

```js
// configurator/public/aircraft.html:378
const s = await fetch("/assets/editor/aircraft_params_schema.json").then(r => r.json());
schema = s;
```

The Worker maps `/assets/*` to an **environment-scoped** R2 key
(`configurator/src/index.ts:44-45`):

```ts
const assetKey = (env, key) =>
  isProdEnv(env) ? key : key.replace(/^assets\/editor\//, `assets/editor/${env}/`);
```

So the same request resolves differently per environment:

| Env | Request | R2 key |
|---|---|---|
| PROD | `/assets/editor/aircraft_params_schema.json` | `assets/editor/aircraft_params_schema.json` (bare) |
| DEV | `/assets/editor/aircraft_params_schema.json` | `assets/editor/dev/aircraft_params_schema.json` |
| QA | `/assets/editor/aircraft_params_schema.json` | `assets/editor/qa/aircraft_params_schema.json` |

The dev/qa objects did not exist, so the `/assets/*` handler returned a JSON 404
(`configurator/src/index.ts:249-257`):

```ts
if (!obj) return c.json({ error: "not found" }, 404);
```

The failure chain on DEV:

1. `fetch(...)` returns **HTTP 404** with body `{"error":"not found"}`.
2. The page does `.then(r => r.json())` with **no `r.ok` check**, so it parses
   the error body: `schema = {error: "not found"}`.
3. `render()` runs `for (const g of schema.groups)` — `schema.groups` is
   `undefined` -> `TypeError: undefined is not iterable` -> `render()` throws.
4. Only the static "Configuration" card remains. Exactly the symptom.

### Evidence (verified 2026-07-15, before the fix)

```
DEV  /assets/editor/aircraft_params_schema.json  -> HTTP 404  {"error":"not found"}
PROD /assets/editor/aircraft_params_schema.json  -> HTTP 200  {"schema_version":1, ...}
```

## Why it got missed

`aircraft_params_schema.json` is generated by **fix-gateway**
(`src/fixgw/tools/export_param_schema.py`), which only writes stdout or `-o
<file>` — it does **not** upload to R2. fix-gateway has no asset-publish
workflow (only `ci.yml`, `coverage.yml`), so this file's entire path to R2 has
always been a manual `wrangler r2 object put` to the bare prefix.

pyEfis's editor schema (`schema.json` / `groups.json`) does *not* have this hole
because `pyEfis/.github/workflows/editor-assets.yml` already maps
`dev/qa/master -> assets/editor/{env}/`. When the DEV/QA prefix scheme landed
(environments.md, 2026-07-08), the hand-uploaded aircraft schema was simply
never taught the new prefixes, so dev/qa were left without it. QA had the same
hole as dev.

## Immediate fix — DONE (2026-07-15)

Copied the prod object to the dev and qa prefixes (purely additive; the bare
prod prefix was never touched):

```bash
# from configurator/  (bucket = makerplane-configs)
npx wrangler r2 object get makerplane-configs/assets/editor/aircraft_params_schema.json --file aps.json --remote
npx wrangler r2 object put makerplane-configs/assets/editor/dev/aircraft_params_schema.json --file aps.json --content-type application/json --remote
npx wrangler r2 object put makerplane-configs/assets/editor/qa/aircraft_params_schema.json  --file aps.json --content-type application/json --remote
```

Post-fix verification:

```
DEV  /assets/editor/aircraft_params_schema.json  -> HTTP 200
QA   /assets/editor/aircraft_params_schema.json  -> HTTP 200
PROD /assets/editor/aircraft_params_schema.json  -> HTTP 200  (untouched)
```

The 404 response set no `cache-control`, so nothing stale is cached; a normal
page load picks up the schema.

## Planned follow-ups (post-demo, both land on `dev` and promote dev -> qa -> prod)

### Plan A — `r.ok` guard in aircraft.html (defensive)

So a missing/renamed asset surfaces a visible error instead of a silent
one-section page.

File: `configurator/public/aircraft.html:378` (and the `boot()` call at line 440).

```js
// replace the fetch+parse:
const r = await fetch("/assets/editor/aircraft_params_schema.json");
if (!r.ok) throw new Error(`aircraft schema unavailable (HTTP ${r.status})`);
schema = await r.json();

// and make boot() failure visible:
boot().catch(e => {
  $("groups").innerHTML =
    `<div class="card"><h2>Couldn't load aircraft parameters</h2>
     <p class="sub">${e.message}. The parameter schema may not be published for
     this environment yet.</p></div>`;
});
```

Risk: low, but it is prod-facing JS; changes only the error path.

### Plan B — durable publish path (the real cause)

Give fix-gateway the same CI treatment pyEfis already has. Add
`fix-gateway/.github/workflows/param-schema-assets.yml`, mirroring
`pyEfis/.github/workflows/editor-assets.yml` but simpler (the generator needs
only a normal `pip install -e .`; it reads `config/database`, no Qt/display):

1. **Trigger:** push to `[dev, qa, master]` on the paths that change the schema —
   `export_param_schema.py` plus the fix-gateway `config/database` source it
   reads (nail down the exact paths by reading the tool's inputs at
   implementation time), plus `workflow_dispatch`.
2. **Generate:** `python -m fixgw.tools.export_param_schema -o work/aircraft_params_schema.json`.
3. **Map branch -> prefix:** `dev -> assets/editor/dev/`, `qa -> assets/editor/qa/`,
   `master -> assets/editor/` (fix-gateway prod branch is `master`).
4. **Upload:** `wrangler@4 r2 object put ${BUCKET}/${PREFIX}aircraft_params_schema.json --remote`,
   with the same skip-green-if-`CLOUDFLARE_API_TOKEN`-unset guard so landing it
   causes no red runs.
5. **Secrets:** fix-gateway becomes a **third** repo needing
   `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` GH secrets. environments.md
   §6 currently says "both repos" — update to three.
6. **Docs:** add fix-gateway to the CI list in `docs/environments.md` §6 as the
   publisher of `aircraft_params_schema.json`.

One-time backfill: when the workflow first reaches `master` it republishes the
bare prod copy identically (no content change) — bringing prod under the same
automation. dev/qa were backfilled by hand today.

Net effect: every push that changes the FIX parameter definitions regenerates
and fans the schema out to all three prefixes automatically — this class of
"asset missing for one env" can't recur.
