# Panel config format — what the editor saves, what the device runs

This explains the file the configuration manager produces when you lay out a
panel, and how it maps to pyEfis. The short version: **the editor saves native
pyEfis config.** There is no separate "design" format and no compile step — the
YAML the editor stores is (almost exactly) the YAML the device loads.

Related: [device_deployment.md](device_deployment.md) (how it reaches the Pi),
[../configurator/README.md](../configurator/README.md) (the app),
[system_designer.md](system_designer.md) (the vision).

## Why no compile step

Earlier drafts had the editor store its own "design" JSON and a server-side step
"compile" it into pyEfis YAML. That's an extra moving part with nothing to gain:
the editor already works in pyEfis's own grid + instrument model, so it just
emits pyEfis config directly. Benefits:

- **One source of truth.** The bytes you see in the editor's Code pane are the
  bytes the device runs. No translation to drift out of sync.
- **The Code pane is real pyEfis config** — editable by hand, copy-pasteable into
  a `screens/` file, reviewable in a PR.
- **Delivery is a file copy**, not a build (see [device_deployment.md](device_deployment.md)).

The only transforms the editor does are mechanical and happen at save time in the
browser (described below): expand element-groups, and strip a couple of
editor-only keys.

## The artifact

A panel is a **pyEfis config fragment**: a `main` block (screen size + which
screen boots) and one screenbuilder `screen`. Example (a small panel):

```yaml
main:
  screenWidth: 1280
  screenHeight: 800
  defaultScreen: PANEL
  screenDiagonalInches: 10.1      # editor metadata; pyEfis ignores unknown main keys
screens:
  PANEL:
    module: pyefis.screens.screenbuilder
    title: Panel
    layout:
      rows: 110
      columns: 200
    instruments:
      - type: airspeed_tape
        row: 6
        column: 4
        span: { rows: 98, columns: 24 }
      - type: atitude_indicator
        row: 6
        column: 68
        span: { rows: 64, columns: 64 }
        options:
          symbol_color: "#ffff00"
      - type: altimeter_tape
        row: 6
        column: 172
        span: { rows: 98, columns: 24 }
```

This is exactly a pyEfis screenbuilder screen plus a `main`. Drop the `screens:`
entry into a device's `screens/` config and set `main.defaultScreen` and it runs.

## Field mapping (editor → pyEfis)

| Editor concept | pyEfis field |
|---|---|
| target resolution (e.g. 1280×800) | `main.screenWidth` / `main.screenHeight` |
| which screen shows on boot | `main.defaultScreen` (always `PANEL`) |
| physical screen size (DPI hint) | `main.screenDiagonalInches` — **editor-only**, pyEfis ignores it |
| the canvas | `screens.PANEL` (`module: pyefis.screens.screenbuilder`) |
| the grid | `screens.PANEL.layout.rows/columns` (always **110 × 200**) |
| each placed widget | an entry in `screens.PANEL.instruments` |

### The grid

pyEfis screenbuilder uses a **normalized 110-row × 200-column grid** — it is the
same regardless of the physical resolution (the layout engine scales the grid to
the real pixels). So a panel laid out at one resolution maps cleanly to another;
the *aspect ratio* is the meaningful variable, which is why the editor targets a
resolution and reflows the canvas to its aspect.

### Instruments

Each instrument is `{ type, row, column, span: { rows, columns }, options }` —
identical to a hand-written screenbuilder instrument. `type` is the pyEfis
widget name (`airspeed_tape`, `atitude_indicator`, `arc_gauge`, …; the full set +
each type's options is the schema the editor loads from
`/assets/editor/schema.json`, generated by `pyefis.editor.schema`). `options` is
omitted when empty. Grid numbers are rounded to one decimal.

## Element groups are expanded

The editor offers **element groups** (e.g. a 4-cylinder CHT/EGT cluster) you drag
in as one unit and can scale together. pyEfis has **no group concept** — a screen
is a flat list of instruments. So at save time the editor **expands** each group
into its child instruments at absolute grid coordinates (the same math as the
editor's *Ungroup*): a child at local grid position within the group's box is
placed at `group.row + child.row/group.gridRows * group.span.rows` (and likewise
for column/spans). The saved YAML therefore contains only concrete instruments.

Consequence: groups are an editing convenience that lives in the canvas, not in
the file. A group still scales/ungroups on the canvas, but the moment the config
is written (or you edit the Code pane) it is flat instruments — re-opening shows
them individually. That's intentional: the file is pure pyEfis.

## Editor-only options that are stripped

`preview_scene` (on `virtual_vfr`) only selects which synthetic-vision *preview
image* the editor shows; it has no meaning on the device and is removed on save.

## Numeric options are written as numbers

An option the schema types `number` or `integer` is saved as a YAML number even
if it was entered as a quoted string (`bg_opacity: '5'` in the Code pane, or a
legacy save) — it is written `bg_opacity: 5`. A blank or non-numeric string on
such an option is dropped on save, so the device uses the option's default.
Options typed `string` (e.g. `font_mask: '00000'`) and options the schema doesn't
declare are written exactly as entered.

## Round-trip + backward compatibility

The editor reads the same format back when you open a device. For older devices
saved before this change, it also accepts the **legacy "design" form**
(`{ kind: pyefis-screen, screen, layout, instruments }`) so they still open; the
next save rewrites them in the native form. (`fromStoredDoc()` /
`toPyefisDoc()` in `public/editor.html`.)

## How it reaches the device

The saved YAML is stored per device (R2 + a versioned `configs` row) and pulled
by the paired device:

```
GET /device/config            Authorization: Bearer <device token>
  -> 200  application/x-yaml   + ETag: "v<n>" | "v<n>-p<hash>"  + X-Config-Version: <n>
          (aircraft references resolved -- see "Aircraft references" below)
  -> 304  (when If-None-Match matches the current ETag — a cheap poll)
  -> 404  no config yet
  -> 401  missing / unknown token
```

### Aircraft preferences block (#108)

A few aircraft-profile settings must reach the device itself, not just the
panel. Today that is only the **altimeter setting units** (aircraft settings ->
Configuration, stored as `profile.meta.baro_unit`, `inHg` default or `hPa`).
The aircraft profile is per project and the panel per device, so the server
joins them at pull time: when the project's active profile sets a unit, the
served YAML gets a top-level block appended after the panel text:

```yaml
preferences:
  units:
    Pressure: hPa       # pyEfis unit group -> unit
```

- The stored panel YAML is not changed and the editor never sees this block;
  it is added to the device response only (`src/device_prefs.ts`). The panel
  text is appended to, not re-serialised, so it reaches the device verbatim.
- **ETag** is `"v<n>"` when the profile sets nothing (unchanged from before) and
  `"v<n>-p<hash>"` otherwise, the hash over the block's content. So changing the
  unit is a new config (no 304), but editing an unrelated profile value is not
  (no needless pyEfis restart). The device stores the ETag it got and sends it
  back as `If-None-Match`.
- On the device, `pyefis-data config-pull` merges `units` into
  `preferences.yaml.custom` (pyEfis reads a top-level `units:` there and starts
  every unit-switching instrument in that group's unit). Other keys in that file
  are left alone, and the merge is covered by the panel snapshot, so a crashed
  install rolls it back too.
- **Unset:** config-pull records which groups it wrote in
  `<config>/.panel_prefs.yaml`. If the profile stops setting a unit (an older
  profile version activated, say), the block is absent and only a group in that
  record is removed, returning pyEfis to its inHg default. A unit set in
  `preferences.yaml.custom` by hand is never touched. A malformed block changes
  nothing.
- `pressure: true` is pyEfis's whole **Pressure** unit group, so `hPa` applies to
  every instrument configured with it, not only the baro box.
- The editor preview reads the same derived block from
  `GET /api/devices/:id/preferences` and shows a `pressure: true`
  `numeric_display` in that unit.

### fix-gateway block: the ownship address (P3f)

The ADS-B traffic writer in fix-gateway drops reports carrying the aircraft's
own 24-bit address (`ownship_address`). The profile holds it as
`meta.registration` (a US N-number derives the address) or `meta.icao_address`
(hex, wins when both are set). When either yields an address, the served YAML
gets a second top-level block:

```yaml
fixgw:
  ownship_address: "AB4549"   # N825V; always quoted, six upper-case hex digits
```

- Absent when the profile sets neither, so the body and ETag are what they
  were. The ETag hash covers this block too; a profile with only a baro unit
  keeps exactly the hash it had before, so adding this block re-pulls no
  device that has no address. A stored panel with its own top-level `fixgw:`
  key gets no second one.
- On the device, `pyefis-data config-pull` writes that one key as a top-level
  `ownship_address:` line (under a marker comment) in fix-gateway's
  `~/makerplane/fixgw/config/preferences.yaml.custom` (`FIXGW_CONFIG_DIR`
  overrides the directory). The file is edited as text, so every other line
  and comment is kept byte-for-byte; the edit is re-parsed and must change only
  that key, or nothing is written. fix-gateway reads the key as the stratux
  connection's `ownship_address` when the connection's own value is blank
  (the fix-gateway change is AER-5468; a fix-gateway without it ignores the
  key, so traffic is filtered by the receiver's own report only).
- The value written is recorded in `.panel_prefs.yaml`. A blank address removes
  the line only if it still holds the recorded value; a hand-edited one stays.
  A malformed block, a missing fix-gateway config dir, or an unreadable
  override changes nothing and is reported.
- fix-gateway (`fixgw` or `fixgateway` unit, user or system scope) is restarted
  only when its file changed. Its override is in the panel snapshot, so a
  crashed install puts it back (or removes a file the install created) and
  restarts fix-gateway again.
- The preview endpoint returns the block as `fixgw` beside `preferences`.

### Aircraft references: a gauge bound to a tank (FUEL1 F3)

A bar or arc gauge can hold a reference to a fuel tank on the aircraft
profile instead of a FIX key: `tank: tk_19c2`, the tank's stable id
([fuel_provider_model.md](fuel_provider_model.md) section 5). The stored panel
keeps only the id. When the config is served, the Worker resolves it against
the project's **active** profile (`resolveAircraftRefs`, `src/aircraft_refs.ts`
over `public/aircraft_refs.js`) and the device receives plain pyEfis options:

```yaml
options:                options:                    options:
  tank: tk_19c2   ->      dbkey: FUELQ3       or      name: L TIP     # its last label
                          name: L TIP                 unbound: true   # no dbkey at all
```

- **Resolved:** `dbkey: FUELQ<slot>` and `name: <label>`; the `tank` key is
  removed. A rename or a rewire on the aircraft page reaches the device on its
  next pull with no panel edit.
- **Orphaned** (the tank was removed, the profile has no fuel group, or there
  is no active profile): no `dbkey`, `unbound: true`, and the label the tank
  last had in any saved profile version (else the panel's own `name`). pyEfis
  draws its failed-sensor state and never looks up a key (pyEfis#452), so a
  removed tank can neither stop pyEfis at boot nor read another tank's value.
- **ETag:** the hash covers the resolved bindings (each gauge's position, id,
  key and label), so a rename, a rewire or a removal is a new config. Editing
  another tank, or any value no binding uses, is not.
- **A panel with no reference** is served exactly as before: the same text,
  unparsed, and the same ETag. A panel with one is parsed and re-dumped the way
  the editor saves it (js-yaml, `lineWidth: 100`), which is how every
  editor-saved panel was written in the first place.
- The same resolver serves three callers, so they cannot disagree:
  `GET /device/config`; **Download YAML** in the editor
  (`GET /api/devices/:id/config/served`, the last saved version exactly as the
  next pull receives it, same ETag); and the editor preview, which imports
  `/aircraft_refs.js` and resolves each gauge before drawing it.
- The picker's data: `GET /api/projects/:id/aircraft/refs?source=aircraft.fuel.tanks`
  (or `/api/devices/:id/aircraft/refs?...`) returns
  `{source, items: [{id, label, slot, role, slot_key}], retired: {id: last label}}`.
  An unknown source is a 400.

Each pull stamps `last_pull_at`. The on-Pi updater then atomic-swaps the screen +
`main` into the device's config (see [device_deployment.md](device_deployment.md),
P3). Because the artifact is already pyEfis config, "install" is a file drop, not
a build.

## Known limitations / follow-ups

- **Synthetic vision data paths.** `virtual_vfr` renders SVS terrain only when its
  `options.svs` block points at the on-device terrain/airport/water data. The
  editor doesn't know a given Pi's data layout, so it does **not** emit those
  paths; the device's `config-pull` injects the `svs:` block (enabled + paths
  under `/data/makerplane-data/...`) at install time, keeping any explicit `svs`
  the panel already carries. Flat `svs_*` editor options override that block
  key by key, as pyEfis resolves them.
- **Legacy Virtual VFR (CIFP) is removed.** pyEfis #457 (VVFR1) deleted the
  legacy CIFP overlay. A `virtual_vfr` is the attitude display with Synthetic
  Vision, which draws airports, runways and a PAPI from the NASR airports pack;
  with SVS off (`svs_enabled: false`) it shows the plain sky/ground attitude
  view. No CIFP download is needed, and `config-pull` adds no
  `screens/virtualvfr_db.yaml` include. The `virtual_vfr` type itself stays:
  it hosts SVS.
- **No `include:` emitted.** The editor places concrete instruments, so it never
  emits pyEfis `include,…` instruments. Stock screens that use includes still
  work on the device; the editor simply doesn't generate them.
- **Aircraft limits / V-speeds / gauge bands** are not in the panel config — they
  come from the FIX database / aircraft config (a separate concern, fix-gateway
  side). The panel only describes *which* instruments go *where*.
